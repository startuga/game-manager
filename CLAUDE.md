# Game Manager

Native Windows 11 game launcher/library written in Rust.

## Layout
- `app/` – WinUI 3 UI built with `windows-reactor` (preview, 0.100). Component/message/view model, Elm style.
  - `main.rs` – window layout: `top_bar` (title, scan status, Add game, Rescan), `sidebar` (search, store filter, game list), `main_panel` (selected game: icon, title, install path, game program, ▶ Play + extra launch buttons, Open folder and Choose game .exe when the install folder is known, Remove for custom games, store, bitness), `add_dialog`/`remove_dialog` (`ContentDialog`s driven by `draft`/`removing` state, attached with `.content_dialog()`: one per view, Add on the top bar, Remove on the body). Selection is kept by game id.
  - Add game: `windows_pickers::OpenFilePicker::request` shows the Open dialog for the app's window (the window is disabled while it is open); the suggested name is then read in a background task. The saved game goes through `gm_core::complete_game` in its background task, so its bitness shows without a rescan.
  - Choose game .exe: `OpenFilePicker` (`*.exe`, opened in the current program's folder or the install folder) records the game's own program with `gm_core::config::set_program` and reads its bitness in a background task (`GameProgramSaved`). Play is not changed; the program is for bitness, Open folder and, later, mods.
  - The game list is wrapped in a keyed `Grid` child whose key (`library::list_key`) hashes the visible game ids: every different set of visible games builds a new `ListView` instead of changing a live one's rows. windows-reactor applies `selected_index` while it is still changing a live list's `DataItem` rows, which selected a row that did not exist yet (`E_INVALIDARG`, the app closed) or left rows showing another game's name (search, select, clear the search). Same ids (icons arriving, an unchanged rescan) keep the list. The reactor has no scroll-into-view, so after clearing a search the highlighted game can be off-screen.
  - `library.rs` – UI-free search/store-filter/selection rules and the list key, unit-tested.
- `core/` (crate `gm-core`) – game discovery, launching, data model. **No UI code here**, so the UI layer can be swapped.
  - `vdf.rs` – Valve KeyValues parsers (text, and binary with inline or string-table keys); `steam.rs` – Steam scanner (program from `appcache\appinfo.vdf` v28/v29: the Windows launch entry, default type before options, 64-bit before unmarked before 32-bit, first existing `.exe`); `epic.rs` – Epic scanner (current launcher: `%LOCALAPPDATA%\com.epicgames.eglv2\installations.jsonl` log + `cache\prod\catalog-cache.json` for titles; legacy: `%ProgramData%` `*.item` manifests); `gog.rs` – GOG scanner (`HKLM\SOFTWARE\WOW6432Node\GOG.com\Games` + each game's `goggame-<id>.info` primary play task; program = the first `game`-category file task whose `.exe` exists, since the primary task may be a launcher such as Witcher 3's `REDprelauncher.exe`); `ea.rs` – EA scanner (folders with `__Installer\installerdata.xml`, found via uninstall entries and `Electronic Arts`/`EA Games` `Install Dir` keys, listed only if the EA app knows them: an `Origin Games\<contentID>` key or an `EAInstaller\...\Cleanup.exe` uninstaller; names from `Origin Games\<contentID>`; program from installerdata `<runtime><launcher>` or the GDF XML resource in `GDFBinary_<locale>.dll`. The EA app's own data is encrypted, so there is no EA-app launch link); `launcher.rs` – `launch` via `ShellExecuteW`; `open_folder` opens the install folder in File Explorer (`ShellExecuteW` "open", or `ILCreateFromPathW` + `SHOpenFolderAndSelectItems` to select `Game::program` when it is directly in the folder; the folder goes through `on_disk_case`, so an Xbox `WindowsApps` link opens as the real `XboxGames` folder; a missing folder is an error). Both run on the UI thread, whose COM apartment the Shell needs.
  - `xbox.rs` – Xbox app / Microsoft Store scanner: the current user's packages from WinRT `PackageManager.FindPackagesByUserSecurityId("")`, kept when the install folder has `MicrosoftGame.config`. Play = `shell:AppsFolder\<PackageFamilyName>!<AppId>` (packaged games cannot be started by their `.exe`); "Open in Xbox app" = `msxbox://game/?productId=<StoreId>`; icon = `Square150x150Logo` (or its largest `scale-`/`targetsize-` variant); arch = the package's `Id().Architecture()` (WinRT `System` feature; `Neutral` falls back to the PE header of the config's first `<Executable Name>`, package files may be unreadable).
  - `pe.rs` – a program's architecture from its PE header (plain file reads, no `unsafe`): `Machine` x86/x64/ARM64/ARM; an x86 IL-only .NET image without `32BITREQUIRED`/`32BITPREFERRED` is `AnyCpu` (64-bit). `Game::program` is the game's own `.exe`, `Game::arch` its `Arch` (`bits()`, `label()`). `complete_game` (run by `scan_all` for every game) fills a missing program from the icon's `.exe` inside the install folder (an EA icon is the game while Play may start a launcher), else the `.exe` Play starts, then reads `arch` unless the scanner set it. Programs are filled before `dedupe_install_dirs`, which hands a dropped duplicate's program to the kept game when it has none (Steam's `steam2ea://` games get the EA scanner's `.exe`).
  - `config.rs` – game configuration in JSON. `config/games.json` (shipped; `core/build.rs` copies it to `target\<profile>\games.json`, read from the running exe's folder or its parent, so it must stay next to `app.exe`; missing = no defaults, malformed = a `ScanReport` error) holds per-game knowledge without store ids, so it works for every store and computer: `games` is a list of known games, each with `programs` (its own binaries relative to the install folder, best first) plus a `name`/`note` for people; a scanned game is the first entry whose binary exists in its install folder, and that binary is its program. `ignoreNamePrefixes` lists names of entries that are not games (e.g. "Steamworks"). `%APPDATA%\Game Manager\game-settings.json` holds the user's per-game settings (`program` from Choose game .exe; unknown fields are kept on save). `apply` runs in `scan_all` right after the store scans (before `default_program` and dedupe, and on custom games): drops ignored entries and sets `program` = user choice (if the file exists; it also clears a package `arch`) > shipped `programs` > the scanner's.
  - `json_file.rs` – where the app's files live and the JSON helpers: `user_file` (`%APPDATA%\Game Manager`, roaming: the user's choices), `local_file` (`%LOCALAPPDATA%\Game Manager`, this computer only: caches, safe to delete), `load` (missing = default, unreadable = error), `save` (temp file + rename).
  - `snapshot.rs` – the last scan's games in `%LOCALAPPDATA%\Game Manager\cache\library.json` (`{ version, games }`, `Game`'s serde form); `load` gives `None` for a missing, unreadable or other-version file. Bump `VERSION` whenever `Game` changes incompatibly. The app saves it in the scan task and shows it at start (`SnapshotLoaded`) only while the first scan is still running and nothing is listed; `Scanned` replaces it.
  - `custom.rs` – games added by hand (`Store::Custom`, ids `custom:<creation ms>`): saved in `%APPDATA%\Game Manager\custom-games.json` (through `json_file`: written via a temp file; an unreadable file is never overwritten). `scan_all` adds them after `dedupe_install_dirs`, so they are never dropped for sharing a folder with a store game. `suggested_name` reads the program's version info (`ProductName`, then `FileDescription`, else the file stem).
  - `text.rs` – shared helpers: UTF-8/UTF-16 file reading, XML declaration stripping, `child_text`.
  - `icon.rs` – game icons as PNG via native APIs (`SHDefExtractIconW` + WIC). `Game::icon` is an `IconRef` (file + index): Steam `Steam App <id>` uninstall `DisplayIcon`, GOG `goggame-<id>.ico`, EA uninstall `DisplayIcon`/`game.ico`, Epic `launchExecutable`, Xbox package logo (PNG/JPEG files are used as they are); otherwise `scan_all` falls back to the Play program. The app loads icons in a second background task after the list is shown. Extracted icons are cached as PNGs in `%LOCALAPPDATA%\Game Manager\cache\icons\<key>.png`, the key being an FNV-1a hash of the icon file's lowercase path, index, pixel size, length, modified time and `CACHE_FORMAT` (bump it when extraction changes); COM/WIC start only on a cache miss. `extract_all` uses the cache; `refresh_all` (full scans only) also prunes unused files. Cache failures only mean "not cached".
  - `Game::launch` is the default Play action; `Game::alt_launches` are optional extra actions (e.g. GOG "Play via Galaxy"). `Launch::Exe` without a `working_dir` starts in the program's own folder.
  - New stores: add a module with `pub fn scan() -> Result<Vec<Game>, String>`, a `Store` variant, and an entry in `SCANNERS` in `lib.rs`. `SCANNERS` order is priority: when two stores report the same install folder, the earlier store keeps the game.
  - `examples/scan.rs` – prints detected games with their bitness, "?" when unknown (headless check of the scanners).

## Toolchain
- Rust pinned to 1.99.1 in `rust-toolchain.toml`, edition 2024, MSVC target.
- windows-rs crates (`windows`, `windows-registry`, `windows-reactor`, `windows-pickers`) always come from the official repository's master branch (https://github.com/microsoft/windows-rs), declared once in the root `[workspace.dependencies]` and used with `workspace = true`. Never switch them back to crates.io. `Cargo.lock` pins the commit; `cargo update` moves to the latest master, then fix whatever its API changes break. The first fetch downloads the whole repository (about 1.4 GB, shallow fetch is nightly-only).
- WinUI apps are framework-dependent: they need the Windows App Runtime 2.x installed.

## Commands
- Build: `cargo build`
- Run UI: `cargo run -p app`
- Scanner check: `cargo run -p gm-core --example scan` (add `-- -v` to print launch commands, icon sources and programs, `-- --icons <dir>` to save every icon as PNG). To verify bitness, compare each `program` with Windows' `GetBinaryTypeW` (kernel32) and the MSVC `dumpbin /headers` `machine` line; names can be wider than their column, so parse scan lines from the right.
- UI check: screen capture does not work from the agent session; inspect the running window with UI Automation (`System.Windows.Automation` in PowerShell) instead. The Open dialog appears under the main window in the UIA tree (class `#32770`), but its Win32 controls show as plain panes and walking them fails while it loads: take the dialog's `NativeWindowHandle`, find the file name box with `GetDlgItem(dlg, 1148)` → child `ComboBox` → child `Edit` and set it with `WM_SETTEXT`, then `PostMessage` `BM_CLICK` to `GetDlgItem(dlg, 1)` (Open). Custom-game checks write to the real `%APPDATA%\Game Manager\custom-games.json`; clean it up afterwards.
- Before finishing a change: `cargo fmt`, `cargo clippy --all-targets` (no warnings), `cargo test`.

## Conventions
- Blocking work (disk scans, registry, network) runs via `ComponentContext::spawn_background` and returns a `Message`; never on the UI thread.
- A store that fails to scan adds to `ScanReport::errors`; it must not hide other stores' games.
- Every `unsafe` block gets a `// SAFETY:` comment.
- No game-specific data in Rust code: knowledge about particular games (their real program when Play starts a launcher, entries that are not games) goes into `config/games.json`, recognised by the game's binaries (never by a store id); the user's choices go into `game-settings.json`. Store file formats and registry locations stay in the scanners.
- Game ids are `<store>:<store id>` and must be stable (used as list keys and, later, for saved data).
- `windows-reactor` is a preview that changes often: when unsure of an API, read the source of the commit in `Cargo.lock` in `~/.cargo/git/checkouts/windows-rs-*/<short rev>/crates/libs/` (`reactor`, `pickers`, and its samples in `crates/samples/`) rather than guessing.
