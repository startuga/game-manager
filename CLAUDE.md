# Game Manager

Native Windows 11 game launcher/library written in Rust.

## Layout
- `app/` – WinUI 3 UI built with `windows-reactor` (preview, 0.100). Component/message/view model, Elm style.
  - `main.rs` – window layout: `top_bar` (title, scan status, Add game, Rescan), `sidebar` (search, filter dropdown: All games / Favorites / each store with games, game list), `main_panel` (selected game: icon, title, install path, game program, ▶ Play + extra launch buttons, Open folder when the install folder is known, PCGamingWiki, Remove for custom games, store, bitness, graphics APIs, then the Game settings and Mods expanders), `add_dialog`/`remove_dialog` (`ContentDialog`s driven by `draft`/`removing` state, attached with `.content_dialog()`: one per view, Add on the top bar, Remove on the body). Selection is kept by game id. `main` shows a message box when the app cannot start (no console would show anything), except for a missing Windows App Runtime, for which the reactor has already offered the install.
  - Add game: `windows_pickers::OpenFilePicker::request` shows the Open dialog for the app's window (the window is disabled while it is open); the suggested name is then read in a background task. The saved game goes through `gm_core::complete_game` in its background task, so its bitness shows without a rescan. The dialog edits a `gm_core::custom::NewGame`.
  - Right-click menu on a list row (Play, Add to / Remove from Favorites): drawn by the app, because windows-reactor attaches a `Menu` only to `Button`/`DropDownButton`/`MenuBarItem` (no context flyout), and `AppContext::show_menu_at` needs `App::run_with` + `open_component_window`, which never exits when the window closes. Each row's content is a `Border` (transparent background, `min_width(ROW_WIDTH)` so the whole row is hit-testable) whose `on_pointer_pressed` sends `RowPointer`; a right-button press selects the game and opens `row_menu` at the pointer (`window_x`/`window_y`). `row_menu_view` adds a last root-grid layer spanning all rows: a transparent backdrop `Border` that closes the menu on any press, and a sibling `Canvas` with the menu (`SolidBackground` card, `Subtle` buttons) kept inside the window via `on_window_size`. The backdrop is not the menu's parent, so pressing an item never closes the menu before the click. Escape closes it through an `on_key_up` handler on the root `Border`, present only while the menu is open. Favorites change at once in `self.games` and are saved by `config::set_favorite` in a background task; a failure sets the flag back.
  - Graphics APIs: `Component::update` runs `handle` (the messages) and then `request_graphics`, so whatever selects a game (a click, a scan, a game added) looks up its APIs once, in the background (`graphics::detect` → `GraphicsDetected`); `graphics`/`graphics_pending` hold the answers by id. `graphics_view` shows them after the bitness ("Checking graphics APIs…" meanwhile, nothing when none was found) with the source as a tooltip, which asks to choose one in Game settings when there are several; an API chosen there (`GameEdits::graphics_api`) shows alone, tooltip "Chosen in Game settings" (so does a chosen bitness). `Component::view` calls `render`.
  - Drop to add: the window's root is a `Border` with a transparent background (so empty areas are hit-testable) and a `drop_policy` accepting storage items (`Link`, caption "Add as a game") only while `can_add_game` (not scanning, picking or with the dialog open, the same rule as the Add game button; otherwise an empty policy shows "not allowed"). `on_drop` → `Message::Dropped` → `NewGame::from_dropped` in a background task (a shortcut is read through COM) → `DraftReady` → the Add a game dialog, filled in.
  - Game settings expander (`game_settings`; open state `settings_open`, kept while switching games): Name, Launch .exe (+ Browse, `*.exe;*.bat;*.cmd`; empty = the store's own launch), Arguments (disabled for Epic/Xbox link launches without a launch .exe, see `gm_core::accepts_args`), Game program (+ Browse, `*.exe`: bitness, Open folder, mods), then side by side the Bitness (32-bit x86 / 64-bit x64, `BITNESS_CHOICES`) and Graphics API (`GraphicsApi::ALL`) drop-downs, whose first item "As detected: …" shows the detected value (a chosen bitness has replaced it in `Game::arch`, so then only "As detected"; the APIs come from `graphics`, so the label changes when detection finishes, which windows-reactor handles without a selection event), Save / Cancel / Reset to detected. Mods such as ReShade and DXVK need the bitness and one API, which is why the user can choose them. `edit.rs` (UI-free, unit-tested) holds the draft: fields start from the game's current values (`EditFields::of`; the choices from `Game::edits`), `EditDraft::for_game` drops a draft once another game is selected or a scan changed the game, and `edits` stores only changed fields (blank name/path = as detected; a new launch .exe also stores the arguments shown). The drop-downs send `EditChoice(EditChoice, Option<usize>)`; `EditFields::choice_index`/`choose` map item 0 to as detected (`None`). windows-reactor's tuple children stop at 16, so the form groups rows. Save checks the paths and calls `config::save_edits`, Reset `config::clear_edits`, both in a background task followed by a Rescan, so `apply` produces name, order, Play, program and bitness in one place.
  - The game list is wrapped in a keyed `Grid` child whose key (`library::list_key`) hashes the visible game ids: every different set of visible games builds a new `ListView` instead of changing a live one's rows. windows-reactor applies `selected_index` while it is still changing a live list's `DataItem` rows, which selected a row that did not exist yet (`E_INVALIDARG`, the app closed) or left rows showing another game's name (search, select, clear the search). Same ids (icons arriving, an unchanged rescan) keep the list. The reactor has no scroll-into-view, so after clearing a search the highlighted game can be off-screen.
  - `library.rs` – UI-free search, `LibraryFilter` (`All`, `Favorites`, `Store(store)`; `filter_options` lists Favorites even at 0 so it can be found), selection rules and the list key, unit-tested; `edit.rs` – the Game settings draft.
  - `mods_view.rs` (`impl GameManager`) – the Mods expander (open state `mods_open`, kept while switching games), after Game settings. DXVK's row: name, the installed version as a `HyperlinkButton` to the page it was downloaded from (`OpenModPage` → `launch`; "Not installed" otherwise), Info, Install DXVK / Reinstall DXVK (wide; "Working…" with a `ProgressRing` while `mod_job` is this game), ⚙ settings, ✕ Uninstall (`FontIcon` in `ThemeBrush::SystemCritical`: `Button` has no foreground), and a hint line below: what Install does (`Target::summary`), what is installed, or the `Blocked` reason (disabled buttons show no tooltips). The API is `dxvk_api`: the one chosen in Game settings, else the detected one when exactly one was found. One `ContentDialog` (`mod_dialog_view`, attached to the main panel's `ScrollViewer`) shows Info (`dxvk::INFO` + this game's target) or DXVK settings (`RadioButtons` variant; while HDR-mod is selected, an "HDR-mod config" `ComboBox` of "None" + the configs for the game's API, with a note: disabled while the list loads, without a single API, or on a failure; then HDR `ToggleSwitch`, frame-rate `NumberBox`, HUD `ComboBox`; Save → `dxvk::save_settings`). The form's rows are a `Vec<View>`, since the config row comes and goes. `update` runs `request_hdr_mod_configs` after `handle`: whenever the dialog shows HDR-mod and the list (`hdr_mod_configs`, once per session; a failure is retried when the dialog opens again) is neither loaded nor loading, `dxvk::hdr_mod_configs` runs in the background → `HdrModConfigsLoaded`. The row's hint names the chosen config. WinUI opens one dialog at a time, so mod buttons wait while any dialog (`mod_dialog`, `draft`, `removing`) is open, and one mod job runs at a time. `mods.json` is loaded at start (`ModsLoaded`) and replaced by what each job returns (`ModJobDone`).
  - `main()` with `--file-ops <encoded>` (`gm_core::mods::FILE_OPS_ARG`) runs `mods::run_encoded` and exits with its code before any UI: that is the copy of the app that `elevate` starts as administrator.
- `core/` (crate `gm-core`) – game discovery, launching, data model. **No UI code here**, so the UI layer can be swapped.
  - `vdf.rs` – Valve KeyValues parsers (text, and binary with inline or string-table keys; objects nest at most `MAX_DEPTH` = 64 levels, so a damaged file is an error, not a stack overflow that would end the app); `steam.rs` – Steam scanner (program from `appcache\appinfo.vdf` v28/v29: the Windows launch entry, default type before options, 64-bit before unmarked before 32-bit, first existing `.exe`); `epic.rs` – Epic scanner (current launcher: `%LOCALAPPDATA%\com.epicgames.eglv2\installations.jsonl` log + `cache\prod\catalog-cache.json` for titles; legacy: `%ProgramData%` `*.item` manifests); `gog.rs` – GOG scanner (`HKLM\SOFTWARE\WOW6432Node\GOG.com\Games` + each game's `goggame-<id>.info` primary play task; program = the first `game`-category file task whose `.exe` exists, since the primary task may be a launcher such as Witcher 3's `REDprelauncher.exe`); `ea.rs` – EA scanner (folders with `__Installer\installerdata.xml`, found via uninstall entries and `Electronic Arts`/`EA Games` `Install Dir` keys, listed only if the EA app knows them: an `Origin Games\<contentID>` key or an `EAInstaller\...\Cleanup.exe` uninstaller; names from `Origin Games\<contentID>`; program from installerdata `<runtime><launcher>` or the GDF XML resource in `GDFBinary_<locale>.dll`, loaded as data through `DataModule`, which frees it on drop. The EA app's own data is encrypted, so there is no EA-app launch link); `launcher.rs` – `launch` via `ShellExecuteW`; `open_folder` opens the install folder in File Explorer (`ShellExecuteW` "open", or `ILCreateFromPathW` (owned by `ItemIdList`) + `SHOpenFolderAndSelectItems` to select `Game::program` when it is directly in the folder; the folder goes through `on_disk_case`, so an Xbox `WindowsApps` link opens as the real `XboxGames` folder; a missing folder is an error). Both run on the UI thread, whose COM apartment the Shell needs.
  - `xbox.rs` – Xbox app / Microsoft Store scanner: the current user's packages from WinRT `PackageManager.FindPackagesByUserSecurityId("")`, kept when the install folder has `MicrosoftGame.config`. Play = `shell:AppsFolder\<PackageFamilyName>!<AppId>` (packaged games cannot be started by their `.exe`); "Open in Xbox app" = `msxbox://game/?productId=<StoreId>`; icon = `Square150x150Logo` (or its largest `scale-`/`targetsize-` variant); arch = the package's `Id().Architecture()` (WinRT `System` feature; `Neutral` falls back to the PE header of the config's first `<Executable Name>`, package files may be unreadable).
  - `graphics.rs` – a game's graphics APIs (`GraphicsApi`: DirectX 8–12, OpenGL, Vulkan; `GraphicsInfo` with its `GraphicsSource`). `detect` (blocking) tries the cache (`%LOCALAPPDATA%\Game Manager\cache\graphics.json`: wiki answers 30 days, file answers 7 days and only while the program's size and modified time are unchanged; a `CACHE` mutex serialises reads and writes), then `pcgamingwiki::api_table` (used as it is: the files are not read when the wiki has the game), then `from_files`; a wiki failure (offline, HTTP 429) falls back to the files uncached. The answer is only a suggestion: when it lists several APIs or a wrong one (a page found by name can be another game, e.g. Dead Space 2008 for the 2023 remake), the user chooses the API in Game settings, so detection keeps no cross-checks or weak heuristics (an era rule against the files and a scan of the program for API DLL names were removed). `from_files` is the fallback, and files alone mislead (tested on 37 games: GTA V imports only `d3d9.dll` but runs D3D11, every Unreal game imports `d3d9.dll`/`opengl32.dll`, plug-ins import D3D11/12, Unity loads its API at run time): it uses the main program's imports (`Game::program`, plus the largest `.exe` when the program is under 5 MB, a launcher or Unreal stub), bundled runtimes and renderer modules named after their API (`D3D12Core.dll`, `shaderapidx9.dll`, `rendersystemvulkan.dll`; install folder to depth 5, at most 2 000 entries, skipping redistributable, installer, `Plugins` and `ThirdParty` folders). Next to DirectX 11/12, DirectX 9 and OpenGL are dropped as helpers. Engine and naming rules only, no game names. `examples/scan.rs --graphics` prints the wiki's and the files' answers, and the API chosen in Game settings, for every game.
  - `http.rs` – minimal HTTPS GETs over WinHTTP (system proxy, 10 s timeouts, redirects followed, `200 OK` or `Error::Http`), with the User-Agent PCGamingWiki and GitHub ask for (`user_agent`): `get(url)` reads an answer of at most 8 MB, `download(url, file)` streams up to 256 MB to a file (no file left on failure). A `Response` owns its request, connection and session `Handle`s (closed on drop, in that order).
  - `mods/mod.rs` – shared mod machinery. `%APPDATA%\Game Manager\mods.json` (`ModsFile`, by game id → `GameMods { dxvk, … }`; unknown fields kept; loaded first, so an unreadable file is never overwritten; `update` holds `FILE_LOCK` and drops empty entries; Reset to detected doesn't touch it) keeps each mod's settings and `Installed { version, page, folder, files (name, size, FNV-1a), backups }`. `plan(previous, folder, files)` gives the `FileOp`s (`Copy`/`Move` to a path that must not exist, `Delete`) that replace a previous install by new files: our files still unchanged are deleted (a file the game replaced since is left), their backups put back, and the game's files in the way set aside as `<name>.gm-backup` (someone else's `.gm-backup` stops the install). `run(ops)` undoes finished ops, last first, when one fails; deletes are renames to `.gm-delete` until the end. `apply(ops)` probes each changed folder with a test file and runs the ops itself, or through `elevate` when one is not writable (Epic/EA under `C:\Program Files`; Steam's and some Epic folders grant Users full control). `run_encoded` (for `--file-ops`) returns 0 or the HRESULT of what failed (`WIN32_ERROR(code).to_hresult()`).
  - `mods/dxvk.rs` – DXVK from https://github.com/doitsujin/dxvk. Stable: `api.github.com/repos/doitsujin/dxvk/releases/latest` → `dxvk-<version>.tar.gz` (folder `dxvk-<version>\x32|x64`). Development: `…/actions/workflows/artifacts.yml/runs?branch=master&status=success&event=push&per_page=1` → run id + commit, `…/actions/runs/<id>/artifacts` → `dxvk-master-<sha>`, downloaded from `https://nightly.link/doitsujin/dxvk/actions/runs/<id>/<name>.zip` (GitHub's own artifact links need a login; the zip has `x32`/`x64` at the top plus the Linux tarball). HDR-mod: `api.github.com/repos/EndlesslyFlowering/dxvk/releases/latest` → `dxvk_v<dxvk>-HDR-mod-v<mod>.7z` (a fork that upgrades render targets and the swap chain for HDR; skip its `-gplasync` assets; version `3.1-HDR-mod-v0.3.4`, so the row's version column is `Auto` with a 150 px minimum). `release_build(release, is_asset)` serves both release variants. HDR-mod ships its own HDR configs at the archive's top (`dxvk_d3d9_<n>_<name>.conf` for Direct3D 8/9, `dxvk_d3d11_and_d3d10_<n>_<name>.conf` for 10/11; 0 = safest, higher upgrade more render targets and may break things; the DLLs are in `normal\x32|x64`): `cached_build` keeps every `.conf` outside `x32`/`x64` in `<version>\configs` (`keep_configs`) and marks a complete build with `.format` = `CACHE_FORMAT` (a folder without it, e.g. an older layout, is downloaded again); `BUILD_LOCK` serialises downloads into the cache, as installs and the config list share its work folder. The list is never hard-coded: `hdr_mod_configs()` reads the latest HDR-mod build's (downloading it if needed), `configs_for(names, api)` keeps the game's family, `config_label` gives "3 – unsafer". `DxvkConfig::hdr_mod_config` (a file name, `hdrModConfig`) starts `dxvk.conf` verbatim (under `# HDR-mod config: <name>`), before our HDR / frame-rate / HUD lines (`DxvkConfig::text(hdr_mod) -> Option<String>`, `None` = no file); `config_text` uses it only with builds that have `configs` (HDR-mod), and refuses a config the build lacks or of another API family (`check_config`), at install and on Save (`save_settings` takes the game's API). Anonymous GitHub API calls: 60 an hour. Builds are kept in `%LOCALAPPDATA%\Game Manager\mods\dxvk\<version>\x32|x64` (only the DLLs of any folder named `x32`/`x64`; moved into place last). `target(game, api)`: x32 for `X86`, x64 for `X64`/`AnyCpu`, ARM blocked; DLLs per API from DXVK's README (8: `d3d8`+`d3d9`; 9: `d3d9`; 10: `d3d10core`+`d3d11`+`dxgi`; 11: `d3d11`+`dxgi`); Direct3D 12 (VKD3D-Proton's job), OpenGL and Vulkan blocked; into the folder of `Game::program`. `install` (latest build of the game's variant; reinstall = one plan replacing the old install), `uninstall`, `save_settings` (only `dxvk.conf` is re-planned). `DxvkConfig` (HDR `dxgi.enableHDR`, `dxgi.maxFrameRate` + `d3d9.maxFrameRate`, `dxvk.hud`) is written as `dxvk.conf` next to the program (DXVK reads it from the working directory), staged in `%LOCALAPPDATA%\Game Manager\mods\staging` and installed like a DLL.
  - `seven_zip.rs` – `extract(archive, dest)` with the shipped `7-Zip\7z.exe` (found by `config::shipped_file`, like `games.json`): `x -y -bso0 -bsp0 -bse0 -o<dest>`, `CREATE_NO_WINDOW` (7-Zip is a console program, the app has none), exit code 0 or 1 is fine; a `.tar.gz` is unpacked twice (the `.tar`, then its files).
  - `elevate.rs` – `run(encoded)`: `ShellExecuteExW` with `runas` (the UAC prompt) and `SEE_MASK_NOCLOSEPROCESS | SEE_MASK_NOASYNC` starts `app.exe --file-ops <percent-encoded JSON ops>`, then `WaitForSingleObject` + `GetExitCodeProcess` (process handle owned by `OwnedHandle`). The ops travel on the command line, so the elevated copy reads no file another program could change in between. No at the prompt is `ERROR_CANCELLED` → `Error::ElevationRefused`; a failure is `Error::Elevated { code }`.
  - `pe.rs` – a program's architecture and imports from its PE headers (plain file reads, no `unsafe`; `Headers`/`Image` find data directories and map RVAs through the section table; `imported_dlls` reads the import and delay-load tables): `Machine` x86/x64/ARM64/ARM; an x86 IL-only .NET image without `32BITREQUIRED`/`32BITPREFERRED` is `AnyCpu` (64-bit). `Game::program` is the game's own `.exe`, `Game::arch` its `Arch` (`bits()`, `label()`). `complete_game` (run by `scan_all` for every game) fills a missing program from the icon's `.exe` inside the install folder (an EA icon is the game while Play may start a launcher), else the `.exe` Play starts, then reads `arch` unless the scanner set it. Programs are filled before `dedupe_install_dirs`, which hands a dropped duplicate's program to the kept game when it has none (Steam's `steam2ea://` games get the EA scanner's `.exe`).
  - `config.rs` – game configuration in JSON. `config/games.json` (shipped; `core/build.rs` copies it to `target\<profile>\games.json`, read from the running exe's folder or its parent, so it must stay next to `app.exe`; missing = no defaults, malformed = a `ScanReport` error) holds per-game knowledge without store ids, so it works for every store and computer: `games` is a list of known games, each with `programs` (its own binaries relative to the install folder, best first) plus a `name`/`note` for people; a scanned game is the first entry whose binary exists in its install folder, and that binary is its program. `ignoreNamePrefixes` lists names of entries that are not games (e.g. "Steamworks"). `%APPDATA%\Game Manager\game-settings.json` holds the user's per-game edits by game id (`GameEdits`: `name`, `launch` program, `args`, `program`, `arch` (`"X86"`/`"X64"`), `graphicsApi` (`"DirectX11"`…), camelCase keys; written by `save_edits`/`clear_edits`, which load first so an unreadable file is never overwritten; unknown fields are kept) and `favorite: true` (`set_favorite`; kept apart from the edits, so Reset to detected does not unfavorite; an entry with nothing left is dropped). `apply` sets `Game::favorite`. `apply` runs in `scan_all` right after the store scans (before `default_program` and dedupe, and on custom games): drops ignored entries; applies edits — `name`; a `launch` that exists becomes `Launch::Exe { path, args, working_dir: None }` (store extras stay); `args` alone go through `with_args` (a program's own arguments, or Steam launch options via `steam::run_uri_with_args`: `steam://run/<appid>//<percent-encoded>/`; Epic/Xbox links unchanged); sets `program` = user's (if the file exists; it also clears a package `arch`) > shipped `programs` > the scanner's; then a chosen `arch` replaces `Game::arch` (`complete_game` only fills a missing one, so it stays and the PE header is not read); and stores the raw edits in `Game::edits` for the panel (the chosen graphics API is read from there).
  - `json_file.rs` – where the app's files live and the JSON helpers: `user_file` (`%APPDATA%\Game Manager`, roaming: the user's choices), `local_file` (`%LOCALAPPDATA%\Game Manager`, this computer only: caches, safe to delete), `load` (missing = default, a UTF-8 byte order mark is skipped, unreadable = error), `save` (temp file + rename).
  - `error.rs` – `gm_core::Error`, one `thiserror` enum for the crate (`Io`/`Json`/`Vdf` with the file's path, `Windows` with what was being worked on, `Http`/`WebJson`/`ResponseTooLarge`/`InvalidUrl` for web requests, `ToolMissing`/`Extract` for 7-Zip, `ElevationRefused`/`Elevated`, `NoRelease`/`NoModBuild`/`NotInstallable` for mods, `NotFound`, `Shell` with `ShellExecuteW`'s code, and the Add game cases), and `gm_core::Result<T>`. `scan_all` reports each failed part as `ScanError { part: ScanPart, error }` (a store, the game configuration or the game settings). The app turns errors into the text it shows with `to_string()` where it receives them, so its `Message`s carry `String`s.
  - `snapshot.rs` – the last scan's games in `%LOCALAPPDATA%\Game Manager\cache\library.json` (`{ version, games }`, `Game`'s serde form); `load` gives `None` for a missing, unreadable or other-version file. Bump `VERSION` whenever `Game` changes incompatibly. The app saves it in the scan task and shows it at start (`SnapshotLoaded`) only while the first scan is still running and nothing is listed; `Scanned` replaces it.
  - `custom.rs` – games added by hand (`Store::Custom`, ids `custom:<creation ms>`): saved in `%APPDATA%\Game Manager\custom-games.json` (through `json_file`: written via a temp file; an unreadable file is never overwritten). `scan_all` adds them after `dedupe_install_dirs`, so they are never dropped for sharing a folder with a store game. `suggested_name` reads the program's version info (`ProductName`, then `FileDescription`, else the file stem). `NewGame` is a game about to be added: `from_program` (a chosen file: suggested name, no arguments) or `from_dropped` (exactly one `.exe`/`.bat`/`.cmd`/`.lnk` among the dropped files; a shortcut gives its file name without `.lnk`, its arguments and its own icon, and must start an existing program: Store apps and folders are refused). `CustomGame::icon` (optional, omitted from the JSON when `None`) is that shortcut icon; `to_game` falls back to the program's icon.
  - `shortcut.rs` – reads a `.lnk` with the Shell's `ShellLink` object (`IShellLinkW` + `IPersistFile::Load`): target (`GetPath`; `read` gives `None` for a shortcut without a file target, such as a Store app), arguments, icon location (`%VAR%` expanded; the target's own first icon counts as none). Its tests write real shortcuts. `com.rs` – `ComGuard` (per-thread `CoInitializeEx`, balanced on drop), used by `icon.rs` and `shortcut.rs`.
  - `text.rs` – shared helpers: UTF-8/UTF-16 file reading, XML declaration stripping, `child_text`, `percent_encode`/`percent_decode`, `fnv1a`.
  - `pcgamingwiki.rs` – `api_table` (a `GraphicsInfo` with source `PcGamingWiki { page }`): the game's `{{API}}` template through the wiki's API, without an account: the page by `action=idlookup` (Steam/GOG ids, exact) or else `action=opensearch` by name, accepted only when the title, letters and digits only, is the name or begins it (the search is fuzzy: "SteamVR" finds "VR Karts SteamVR"); then `action=parse&prop=wikitext`, whose `direct3d versions` give major versions 8–12 (`9.0c`, `9Ex`, `10.1`) and `opengl`/`vulkan versions` count unless empty or `false`. Requests go one second apart (`LAST_REQUEST`), as the wiki asks (60/minute, 429 blocks for 60 s). `page_url`: the game's PCGamingWiki address, which the app's PCGamingWiki button opens in the browser through `launch` (`Launch::Uri`). Links need no request: Steam games use `https://www.pcgamingwiki.com/api/appid.php?appid=<AppID>`, GOG games `…/api/gog.php?page=<product id>` (the wiki's id redirects go straight to the article, with no Cloudflare check; an id the wiki doesn't know shows "No such AppID"), everything else `…/w/index.php?search=<name>` with ™ ® © removed (the article when the name is its title, else the results page, behind a Cloudflare "confirm you are human" check in a fresh browser). `cargoquery` (the wiki's structured data) needs a bot-password login since Aug 2026, hence the wikitext.
  - `icon.rs` – game icons as PNG via native APIs (`SHDefExtractIconW`, its handle owned by `OwnedIcon`, + WIC). `Game::icon` is an `IconRef` (file + index): Steam `Steam App <id>` uninstall `DisplayIcon`, GOG `goggame-<id>.ico`, EA uninstall `DisplayIcon`/`game.ico`, Epic `launchExecutable`, Xbox package logo (PNG/JPEG files are used as they are); otherwise `scan_all` falls back to the Play program. The app loads icons in a second background task after the list is shown. Extracted icons are cached as PNGs in `%LOCALAPPDATA%\Game Manager\cache\icons\<key>.png`, the key being an FNV-1a hash of the icon file's lowercase path, index, pixel size, length, modified time and `CACHE_FORMAT` (bump it when extraction changes); COM/WIC start only on a cache miss. `extract_all` uses the cache; `refresh_all` (full scans only) also prunes unused files. Cache failures only mean "not cached".
  - `Game::launch` is the default Play action; `Game::alt_launches` are optional extra actions (e.g. GOG "Play via Galaxy"). `Launch::Exe` without a `working_dir` starts in the program's own folder.
  - New stores: add a module with `pub fn scan() -> gm_core::Result<Vec<Game>>`, a `Store` variant, and an entry in `SCANNERS` in `lib.rs`. `SCANNERS` order is priority: when two stores report the same install folder, the earlier store keeps the game.
  - `examples/scan.rs` – prints detected games with their bitness, "?" when unknown (headless check of the scanners).

## Toolchain
- Rust pinned to 1.99.1 in `rust-toolchain.toml`, edition 2024, MSVC target.
- windows-rs crates (`windows`, `windows-registry`, `windows-reactor`, `windows-pickers`) always come from the official repository's master branch (https://github.com/microsoft/windows-rs), declared once in the root `[workspace.dependencies]` and used with `workspace = true`. Never switch them back to crates.io. `Cargo.lock` pins the commit; `cargo update` moves to the latest master, then fix whatever its API changes break. The first fetch downloads the whole repository (about 1.4 GB, shallow fetch is nightly-only).
- WinUI apps are framework-dependent: they need the Windows App Runtime 2.x installed.
- 7-Zip ships with the app: `tools/7-Zip` holds `7z.exe`, `7z.dll` (7-Zip 26.05 x64) and its `License.txt` (GNU LGPL; the notice must ship with them). `core/build.rs` copies the folder to `target\<profile>\7-Zip`, next to `app.exe`, like `games.json`. To update it, copy the same three files from a newer 7-Zip install.
- Every dependency's version is in the root `[workspace.dependencies]`. `[workspace.lints]` (each crate opts in with `[lints] workspace = true`): `undocumented_unsafe_blocks` and `dbg_macro` deny; `multiple_unsafe_ops_per_block`, `unwrap_used`, `expect_used` and `todo` warn. `clippy.toml` allows unwrap/expect in tests; `build.rs` and `examples/scan.rs` allow `expect` with a reason.
- Release profile: `lto`, `codegen-units = 1`, `strip` (app.exe 3.88 → 3.34 MB; a clean release build takes about twice as long).

## Commands
- Build: `cargo build`
- Run UI: `cargo run -p app`
- Scanner check: `cargo run -p gm-core --example scan` (add `-- -v` to print launch commands, icon sources, programs and PCGamingWiki links, `-- --graphics` to compare every game's graphics APIs from the wiki and from its files, and show the chosen one (about 2 s a game), `-- --icons <dir>` to save every icon as PNG). To verify bitness, compare each `program` with Windows' `GetBinaryTypeW` (kernel32) and the MSVC `dumpbin /headers` `machine` line; names can be wider than their column, so parse scan lines from the right.
- UI check: screen capture does not work from the agent session; inspect the running window with UI Automation (`System.Windows.Automation` in PowerShell) instead. The Open dialog appears under the main window in the UIA tree (class `#32770`), but its Win32 controls show as plain panes and walking them fails while it loads: take the dialog's `NativeWindowHandle`, find the file name box with `GetDlgItem(dlg, 1148)` → child `ComboBox` → child `Edit` and set it with `WM_SETTEXT`, then `PostMessage` `BM_CLICK` to `GetDlgItem(dlg, 1)` (Open). Custom-game checks write to the real `%APPDATA%\Game Manager\custom-games.json`; clean it up afterwards. Drag and drop and right-clicks cannot be tested from the agent session: it has no input desktop (`SetCursorPos` fails, the cursor reads 0,0, no foreground window), so synthetic drags never start; ask the user to drop a file on a build they run themselves.
- Mod check: never install into the user's real games (their folders may hold their own DXVK/ReShade). Add a throwaway custom game instead (a temp folder with a copy of `SysWOW64\notepad.exe` as `game.exe` and a fake `d3d9.dll`; an entry in `custom-games.json` and `"graphicsApi": "DirectX9"` in `game-settings.json`, both backed up and restored, and `mods.json` removed afterwards), then drive Install / Settings / Reinstall / Uninstall with UI Automation and compare the folder with how it started. `app.exe --file-ops <percent-encoded ops>` can be run directly (not elevated) to check that path. The UAC prompt cannot be answered from the agent session: ask the user to test a protected folder.
- Before finishing a change: `cargo fmt`, `cargo clippy --all-targets` (no warnings), `cargo test`.

## Conventions
- Blocking work (disk scans, registry, network) runs via `ComponentContext::spawn_background` and returns a `Message`; never on the UI thread.
- A store that fails to scan adds to `ScanReport::errors`; it must not hide other stores' games.
- Every `unsafe` block holds one unsafe operation and gets a `// SAFETY:` comment (Clippy enforces both). A handle that must be freed is owned by a small type whose `Drop` frees it (`OwnedIcon`, `DataModule`, `ItemIdList`, `ComGuard`), so no early return or panic can leak it.
- gm-core returns `gm_core::Result<T>` with a `gm_core::Error` variant, never a `String` error; give a new failure its own variant when a caller may want to tell it apart.
- No game-specific data in Rust code: knowledge about particular games (their real program when Play starts a launcher, entries that are not games) goes into `config/games.json`, recognised by the game's binaries (never by a store id); the user's choices go into `game-settings.json`. Store file formats and registry locations stay in the scanners.
- Game ids are `<store>:<store id>` and must be stable (used as list keys and, later, for saved data).
- `windows-reactor` is a preview that changes often: when unsure of an API, read the source of the commit in `Cargo.lock` in `~/.cargo/git/checkouts/windows-rs-*/<short rev>/crates/libs/` (`reactor`, `pickers`, and its samples in `crates/samples/`) rather than guessing.
